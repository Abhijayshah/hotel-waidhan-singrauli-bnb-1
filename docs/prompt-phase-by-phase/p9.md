# PHASE 9 — Production Deployment, Custom Domain, Monitoring & Go-Live Verification

## 1. Role and Context

Continue the existing project:

`hotel-waidhan-singrauli-bnb-nextjs`

## 2. Objective

Prepare the application for production and, where credentials and authorization are available, deploy it safely.

The final outcome should include:

- A successful production build.
- A documented deployment configuration.
- Secure environment variables.
- Supabase production configuration.
- Domain and HTTPS setup instructions.
- Database migration and recovery procedures.
- Search engine verification preparation.
- Operational monitoring and health checks.
- A complete go-live checklist.
- A truthful production verification report.

Do not claim the website is live unless its deployment and public accessibility have actually been verified.

## 3. Hosting and Deployment Assessment

Inspect the current project and select the most suitable Next.js-compatible hosting provider, prioritizing the existing architecture and configuration.

Consider Vercel as the default candidate unless the current implementation has a justified reason to use another provider.

Check:

- Next.js version compatibility.
- App Router and Route Handler support.
- Server-side execution requirements.
- Environment variable support.
- Build and deployment settings.
- Image optimization requirements.
- Supabase connectivity.
- Email notification requirements.
- Background notification processing, if implemented.
- Hosting limits relevant to the actual application.

Do not add a second hosting platform unnecessarily.

Document the selected platform, why it fits, expected limitations, and any costs that require owner approval.

Do not purchase a subscription or enable a paid service without authorization.

## 4. Git and Repository Safety

Before deployment:

1. Inspect the current Git branch and working tree.
2. Identify uncommitted changes and untracked files.
3. Verify `.gitignore` excludes local environment files, build artifacts, and other sensitive material.
4. Confirm `.env.example` contains placeholders rather than actual secrets.
5. Inspect tracked files for accidental credentials.
6. Ensure migrations and essential documentation are committed or otherwise preserved.

Do not delete, reset, or overwrite the user's changes.

Do not force-push, rewrite Git history, or commit secrets.

If a required Git remote is missing, document how to configure it rather than inventing a repository URL.

## 5. Environment Configuration

Create a production environment variable inventory covering:

- Supabase project URL.
- Supabase publishable or anonymous public key, as appropriate.
- Server-side database connection.
- Authentication configuration.
- Email provider credentials, if used.
- Application base URL.
- Any genuinely required rate-limiting or monitoring configuration.

Requirements:

- Use platform-managed environment variables for production secrets.
- Keep privileged keys server-only.
- Never expose `DATABASE_URL`, service-role keys, email API keys, or other secrets to client bundles.
- Do not commit `.env.local` or production `.env` files.
- Validate required environment variables at startup or at the relevant server boundary.
- Provide actionable configuration errors without printing secret values.
- Keep development, preview, and production environments separate where supported.

Do not create fake credentials or claim an external integration is operational without testing it.

## 6. Supabase Production Setup

Review the existing Supabase project configuration and database migrations.

Document or implement, where authorized:

- Production project configuration.
- Authentication site URL and allowed redirect URLs.
- Required environment variables.
- Database schema migration procedure.
- Row-Level Security verification.
- Database indexes and constraints.
- Database connection settings appropriate to the hosting runtime.
- Email authentication configuration if used.
- Safe handling of connection pooling and serverless execution.

Before applying migrations, inspect the migration history and determine whether the operation is safe.

Do not reset a production database, drop tables, delete customer records, or apply destructive migrations.

Use a staging environment or disposable test database for migration validation when available.

If production credentials are unavailable, prepare the instructions and stop short of claiming that the live database has been configured.

Verify:

- Lint.

- Unit tests.
- Integration tests where configured.
- Production build.
- Environment variable validation.
- Migration consistency.
- Route generation and metadata.
- Server-only module boundaries.
- No accidental dependence on local files or development-only services.

Use the package manager and scripts already established in the repository.

Deploy through the selected platform only when access and authorization are available.

Do not change production traffic, remove a working deployment, or replace DNS records without explicit approval.

If deployment cannot be completed, provide precise manual deployment instructions and clearly identify the missing dependency.

## 8. Custom Domain and HTTPS

Use the approved website domain:

`https://hotelwaidhanbnb.com`

Check whether the domain is already configured and whether an existing deployment uses it.

Prepare the domain setup for the selected hosting platform, including:

- Adding the domain to the hosting project.
- Verifying domain ownership if required.
- Configuring only the DNS records specified by the provider.
- Enabling HTTPS.
- Checking certificate issuance.
- Selecting a canonical hostname.

Do not assume the domain is owned or accessible merely because it appears in the strategy documents.

If DNS access is unavailable, produce a checklist for the domain owner.

## 9. SEO and Search Engine Go-Live

Verify the production site after deployment.

- HTTP to HTTPS behavior.
- Canonical hostname redirects.
- Page titles and meta descriptions.
- Canonical URLs.
- `robots.txt`.
- `sitemap.xml`.
- Structured data validity.
- Open Graph metadata.
- Internal navigation links.
- 404 handling.
- Indexability of intended public pages.
- Noindex behavior for private utility pages.
- Exclusion of admin pages and API routes from the sitemap.

Prepare Google Search Console verification instructions and sitemap submission steps.

Do not claim indexing, rankings, or Search Console verification unless these have actually been checked.

Do not add fabricated reviews, business details, or structured-data values.

## 10. Operational Monitoring and Health Checks

Implement or verify an appropriate health-check endpoint, such as `/api/health`, returning only safe operational information.

Requirements:

- Do not expose environment variables, stack traces, database connection strings, or customer information.
- Distinguish application health from optional dependency health.
- Avoid exposing sensitive infrastructure details to unauthenticated visitors.
- Use short timeouts for dependency checks.
- Avoid a health endpoint that triggers expensive queries.
- Document the intended monitoring behavior.

If a separate readiness endpoint is necessary, keep its output minimal and safe.

Document monitoring for:

- Failed booking enquiries.
- Database connectivity issues.
- Failed notification processing.
- Unexpected server errors.
- Authentication configuration problems.

If an external monitoring provider is not configured, provide an integration point and setup guide instead of claiming monitoring is active.

## 11. Production Booking Workflow Verification

Run a controlled end-to-end test using clearly identified test data in a staging or isolated environment.

Verify:

1. A visitor can open the accommodation pages.
2. The booking enquiry form validates its inputs.
3. A valid enquiry is persisted.
4. The customer sees an accurate acknowledgement.
5. An authorized staff member can retrieve the enquiry.
6. Staff can update its status according to the defined rules.
7. Unauthorized users cannot view private enquiry details.
8. Notification processing behaves correctly when configured.
9. A confirmed status is not set automatically by public form submission.
10. Public contact and WhatsApp links work.

Use synthetic test data only in the designated test environment.

Do not submit test bookings into a live operational workflow without explicit authorization.
