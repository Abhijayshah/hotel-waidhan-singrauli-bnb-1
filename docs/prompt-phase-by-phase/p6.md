# PHASE 6 — Admin Dashboard, Enquiry Management & Role-Based Staff Interface

## 1. Role and Project Context

Act as a senior Next.js engineer, product designer, and application security specialist.

Continue the existing project:

`hotel-waidhan-singrauli-bnb-nextjs`

Before making changes, inspect the codebase and read the approved website strategy, Phase 1–5 documentation, database schema, authentication implementation, security review, and test reports.

Preserve all completed work. Do not recreate the application, replace the design system, or break public website pages, SEO, navigation, mobile responsiveness, or booking enquiry submission.

## 2. Phase Objective

Build a professional, responsive, database-backed administration interface for Hotel Waidhan Singrauli BNB.

Authorized staff should be able to:

- Sign in securely.
- View an operational dashboard.
- View, search, filter, and paginate booking enquiries.
- Open enquiry details.
- Update enquiry status.
- Assign enquiries to staff where supported by the schema.
- Add internal notes with restricted access.
- Manage accommodation categories and their public-facing content.
- View a basic audit history of relevant administrative actions.
- Access only the functions allowed by their role.

All displayed operational data must come from the configured backend. Do not use fake statistics or pretend that sample data represents real customers.

## 3. Admin Routes

Implement a consistent protected route structure, adapting to the existing project:

- `/admin/login`
- `/admin` — dashboard overview
- `/admin/enquiries` — enquiry list
- `/admin/enquiries/[id]` — enquiry details
- `/admin/accommodations` — accommodation category management
- `/admin/audit-logs` — restricted audit history
- `/admin/settings` — basic account and configuration information, only where supported

Protect every route and its underlying data operations on the server. Hiding a navigation link is not authorization.

Unauthenticated users should be redirected to login or receive an appropriate unauthorized response. Authenticated users without the required permission must receive a forbidden response or a safe access-denied page.

## 4. Dashboard Design

Use the existing design system, typography, color tokens, buttons, cards, and responsive layout.

Build a polished hospitality operations dashboard featuring:

- Sidebar navigation on desktop.
- Collapsible or compact navigation on smaller screens.
- Header with page title, current user, role, and sign-out action.
- Mobile-friendly navigation and forms.
- Consistent loading, empty, error, and success states.

Display operational metrics only when they can be calculated from actual database records, such as:

- Total enquiries.
- New enquiries awaiting attention.
- Enquiries contacted.
- Pending confirmations.
- Confirmed bookings, if this status is supported and genuinely represents staff-confirmed reservations.
- Recent enquiries.

Use clearly defined date ranges for time-dependent metrics. Avoid unsupported revenue, occupancy, conversion, or availability claims.

If the database is not configured, show an explicit setup or connection state rather than fabricated data.

## 5. Enquiry Management

Build a searchable and paginated enquiry table with:

- Enquiry reference.
- Guest name.
- Contact information, visible only to authorized staff.
- Requested accommodation.
- Check-in and check-out dates.
- Guest count.
- Current status.
- Submission date.
- Assigned staff member, where implemented.

Provide practical filters for:

- Enquiry status.
- Accommodation category.
- Check-in date range.
- Submission date range.

Implement search and pagination on the server where appropriate. Validate filter inputs and enforce sensible pagination limits.

The enquiry detail page should show the complete authorized record, relevant status history if available, and internal notes.

### Status updates

Allow authorized staff to transition enquiries through the statuses defined in the Phase 5 schema.

Requirements:

- Validate status changes on the server.
- Enforce role-based permissions.
- Prevent arbitrary client updates to protected fields.
- Record meaningful changes in the audit log.
- Provide a confirmation step for consequential changes.
- Show clear success or error feedback.

A submitted enquiry is not a confirmed reservation. Staff must explicitly confirm a reservation only after the business has verified it.

Do not invent room availability or automatically allocate rooms.

## 6. Internal Notes and Staff Assignment

If the Phase 5 schema supports internal notes and staff assignment, implement them securely.

Internal notes must never appear on public pages, customer-facing API responses, or public booking confirmation screens.

Only authorized roles may read or write internal notes.

Staff assignment must reference legitimate staff profiles and must not allow arbitrary user IDs supplied by the browser.

If schema changes are needed, add safe, version-controlled migrations. Do not perform destructive production migrations.

## 7. Accommodation Management

Build an interface to manage accommodation category content stored in the database.

Support appropriate fields already defined by the schema, such as:

- Accommodation name.
- URL slug.
- Description.
- Publication status.
- Display order.
- Optional image reference.
- Optional configurable public-facing features.

Validate all fields on the server. Enforce unique slugs and safe text limits.

Do not invent prices, inventory quantities, room counts, amenities, facilities, or occupancy rules.

If pricing fields are not yet implemented, do not introduce arbitrary prices. If image uploads are not configured, accept only safe existing image references or defer uploads to a later phase.

Preserve existing SEO-friendly public routes and ensure accommodation edits do not silently break their URLs.

## 8. Authentication and Role Permissions

Use the existing Phase 5 Supabase Auth integration and authorization helpers.

Define permissions centrally. A reasonable starting model is:

- `super_admin`: full administrative access.
- `admin`: manage operational enquiries and accommodation content.
- `manager`: manage permitted operational records.
- `staff`: access only the operational actions explicitly granted.

Review every permission against actual business requirements and implement least privilege.

Requirements:

- Check identity and authorization on every protected server action and API route.
- Never trust client-supplied roles or user IDs.
- Do not allow users to promote themselves.
- Do not expose service-role keys to browser bundles.
- Ensure staff cannot access unauthorized records or internal notes.
- Implement safe sign-out and session handling.
- Do not seed a production administrator with a hardcoded password.

If there is no secure way to create the first administrator, document the controlled setup procedure instead of adding a public admin-registration route.

## 9. Backend and Data Access

Reuse the existing Drizzle schema, Supabase Auth setup, validation schemas, and data-access layer wherever possible.

Add server-side functions or route handlers for:

- Dashboard metrics.
- Enquiry list and filtering.
- Enquiry detail retrieval.
- Enquiry status changes.
- Staff assignment.
- Internal note operations.
- Accommodation CRUD operations.
- Audit-log retrieval.

Use shared Zod validation for all mutations.

Ensure database queries are appropriately scoped and paginated. Avoid loading every enquiry into memory to perform client-side filtering.

Use transactions when multiple database changes must succeed together. Keep audit logging consistent with the operation being recorded.

Return safe errors and avoid logging guest personal information.

## 10. User Experience

Implement:

- Skeletons or suitable loading indicators.
- Helpful empty states.
- Clear validation messages.
- Toasts or inline success/error feedback using the existing UI patterns.
- Accessible form labels and keyboard navigation.
- Responsive tables or mobile-friendly record layouts.
- Confirmation dialogs for important changes.
- Disabled states during submission to prevent duplicate mutations.
- A consistent not-found state for invalid enquiry IDs.

Do not add decorative charts unless real data and a clear operational use case justify them.

## 11. Security Testing

Add or extend automated tests for:

- Unauthenticated access to admin routes.
- Insufficient role permissions.
- Staff access to unauthorized records.
- Attempts to alter protected fields.
- Invalid enquiry status transitions.
- Unauthorized internal-note access.
- Invalid accommodation mutations.
- Duplicate accommodation slugs.
- Pagination and filter validation.
- Audit logging of important changes.
- Safe handling of database errors.

Test server-side authorization directly; UI-only permission checks are insufficient.

Verify that public routes and booking enquiry submission continue to work.
