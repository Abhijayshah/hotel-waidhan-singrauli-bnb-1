# PHASE 2 — Design System, Shared Layout & Responsive UI

## Role
Act as a senior UI/UX designer, design systems engineer, accessibility specialist, and Next.js App Router developer.

## Objective
Implement a polished, reusable, production-oriented design system for **Hotel Waidhan Singrauli BNB (Comfort Stay & PG)**.

Phase 1 created the new project foundation. Phase 2 must build upon the actual code and configuration present in that project. Do not assume files or dependencies exist without inspecting them.

**This phase builds the shared visual foundation, not the entire website.** Preserve the existing hotel project and all reference documentation.

## 1. Inspect Phase 1

Before coding:

1. Read `docs/development/PHASE-1-FOUNDATION.md`, `docs/development/PHASE-1-TEST-REPORT.md`, `docs/development/OPEN-QUESTIONS.md`, and the project `README.md`, if present.
2. Inspect `package.json`, `src/app/layout.tsx`, `src/app/globals.css`, `src/app/page.tsx`, Tailwind configuration, TypeScript configuration, and central site configuration.
3. Check the installed Next.js and Tailwind versions and use their appropriate configuration conventions.
4. Inspect the approved reference documents under `docs/reference/`, especially the brand and design system specification.
5. Identify any Phase 1 issues that would prevent Phase 2 from working. Fix only directly related foundation issues and document them.

Do not overwrite existing work blindly.

## 2. Brand and design tokens

Implement the following approved design direction using centralized CSS custom properties and Tailwind utilities where appropriate.

### Color palette
- Deep navy: `#0F172A`
- Slate: `#1E293B`
- Primary amber: `#D97706`
- Hover amber: `#F59E0B`
- WhatsApp green: `#25D366`
- Light background: `#F8FAFC`
- Light surface: `#FFFFFF`

Define semantic tokens for:
- Page background and surface
- Primary and secondary text
- Muted text
- Primary and secondary buttons
- Borders and dividers
- Focus rings
- Links
- Success, warning, and error states
- Header, footer, and overlay surfaces
- Shadows and elevation
- Spacing, container widths, radii, and typography scale

Ensure readable contrast in every supported theme. Do not scatter arbitrary hex codes throughout components.

### Typography
Use Outfit for headings and Inter for body text, consistent with the strategy.

Use `next/font/google` if the fonts can be fetched in the build environment. If the build environment cannot access Google Fonts, use a robust system-font fallback and document the limitation. Avoid loading fonts repeatedly in individual components.

Establish responsive font sizes, weights, line heights, paragraph spacing, and heading hierarchy.

## 3. Theme support

Implement:
- Light theme
- Dark theme
- System theme that follows the user's operating-system preference

Requirements:
- A reusable `ThemeProvider` and accessible `ThemeToggle`.
- Persist the user's explicit choice where appropriate.
- System mode should update when the OS preference changes.
- Prevent or minimize flash of incorrect theme during initial render.
- Avoid hydration mismatch and unsafe direct access to `window` during server rendering.
- Use a maintained, compatible theme library only if it is already installed or justified by the project's actual framework setup.
- Theme selection must be usable with a keyboard and assistive technology.

If using a theme library, configure it correctly for the installed Next.js version and document the choice.

## 4. Shared layout components

Build reusable components in appropriate locations within `src/components/layout/` and `src/components/ui/`.

### Header
- Brand wordmark using “Hotel Waidhan Singrauli BNB”.
- Optional descriptor: “Comfort Stay & PG”.
- Responsive desktop navigation.
- Mobile menu with an accessible open/close control.
- Clear primary booking/enquiry CTA.
- Theme toggle.
- Keyboard-visible focus states and appropriate active-link treatment.
- Prevent navigation overflow at tablet and intermediate desktop widths.

### Footer
- Brand name and concise description.
- Navigation links to the approved primary routes.
- Contact and location section using central site configuration.
- Call and WhatsApp links only when their configured values are valid.
- Privacy, terms, cancellation, and guest-policy links when the routes exist.
- No invented business registration numbers, reviews, awards, or certifications.

### Mobile navigation
- Use an accessible drawer or menu.
- Close after navigation.
- Support Escape to close and proper focus behavior.
- Prevent background scrolling while an open modal/drawer requires it.
- Avoid duplicate navigation elements being exposed to screen readers.

### Sticky mobile action bar
Prepare a responsive bottom action bar for small screens with:
- Call Reception
- WhatsApp Desk

Requirements:
- Use the central site configuration for contact information.
- Maintain minimum 48 × 48 px interactive targets.
- Respect device safe-area insets.
- Do not obscure page content, form buttons, or footer content.
- Hide or adjust it where it would conflict with another modal or primary action.
- Never render fake or placeholder contact links as active actions.

### Reusable UI primitives
Implement a small, consistent set of components:
- `Button`
- `Container`
- `SectionHeading`
- `Card`
- `Badge`
- `IconButton`
- `Input`
- `Textarea`
- `Select`
- `ThemeToggle`

Use proper TypeScript types, semantic HTML, and accessible labels. Avoid unnecessary abstractions or overly complex component APIs.

Use an existing icon library if already installed. Otherwise, select a small compatible library only if needed. Do not use emoji as substitutes for important interface icons.

## 5. Navigation configuration

Keep navigation items in a central configuration file rather than hardcoding separate copies in the header, mobile menu, and footer.

Use only approved routes that actually exist. For routes scheduled for later phases, either omit the link temporarily or provide a deliberate, working destination. Do not create a large collection of empty placeholder pages merely to fill the navigation.

Preserve the planned URL strategy from the approved sitemap.

## 6. Responsive design requirements

Test and refine the layout at representative viewport widths:
- 320 px
- 375 px
- 640 px
- 768 px
- 1024 px
- 1280 px
- 1440 px

Requirements:
- No unintended horizontal overflow.
- Text remains readable without excessive shrinking.
- Navigation remains usable across breakpoints.
- Cards, forms, buttons, and layout containers adapt naturally.
- Images preserve aspect ratios.
- Touch targets are large enough for mobile use.
- The sticky action bar does not cover important content.

Use a mobile-first approach rather than desktop layouts scaled down without redesign.

## 7. Accessibility and quality

Implement:
- Semantic landmarks (`header`, `nav`, `main`, `footer`).
- Skip-to-content link.
- Keyboard navigation.
- Visible focus indicators.
- Accessible names for icon-only controls.
- Correct form labels and error-state hooks.
- Appropriate ARIA attributes only where necessary.
- Reduced-motion support.
- WCAG-aware contrast for text and controls.
- Correct heading order.

Do not claim WCAG compliance without testing it.

## 8. Homepage integration

Update the existing homepage only as needed to demonstrate the shared design system.

Include:
- Shared header.
- A restrained, well-designed introductory hero.
- A primary room-enquiry CTA.
- A secondary call/WhatsApp CTA when configured.
- A small accommodation-category preview.
- Shared footer.
- Mobile action bar.

Use actual assets if present in the new project's `public/` directory. Do not invent photographs or present stock imagery as actual hotel photos. If the hotel photography is unavailable, use an intentional, attractive placeholder that is clearly replaceable.

Do not build all accommodation pages, booking backend, admin dashboard, or payment gateway in this phase.

## 9. Project architecture

Keep server components as the default.

Use client components only where interaction requires them, such as:
- Theme selection
- Mobile navigation
- Interactive controls

Keep static site configuration and presentational components server-compatible wherever possible.

Avoid:
- Duplicated CSS systems.
- Repeated hardcoded business information.
- Unnecessary global client state.
- Unnecessary dependencies.
- Unsafe HTML injection.
- Exposing secrets in client bundles.
