## 2. Pages to implement

Implement these six customer-facing routes:

1. `/` — Homepage
2. `/rooms` — Rooms and accommodation catalogue
3. `/rooms/deluxe-ac-room` — Deluxe AC room
4. `/rooms/standard-room` — Standard Non-AC room
5. `/rooms/dormitory` — Single-bed dormitory
6. `/rooms/pg-rooms` — Monthly PG and long-stay accommodation

All routes must work through direct URL navigation, page refresh, and internal links.

Use a shared page layout and reusable room components rather than copying large blocks of JSX between pages.

## 3. Homepage design

Create a high-quality, mobile-first homepage with the following sections.

### A. Header and hero

Reuse the shared header and theme system from Phase 2.

Include:

- Clear Hotel Waidhan Singrauli BNB branding.
- A concise value proposition for budget accommodation in Waidhan, Singrauli.
- A primary CTA to explore rooms.
- A secondary call or WhatsApp enquiry CTA when valid contact information is configured.
- A hero image only if a suitable real hotel image exists in the project.
- A replaceable, clearly identified placeholder if real photography is unavailable.

Do not fabricate actual hotel photos or represent stock photography as the real property.

### B. Quick enquiry panel

Build a lightweight enquiry widget with:

- Check-in date.
- Check-out date.
- Number of guests.
- Accommodation type.
- Submit/enquire action.

Validate dates and required fields on the client. Prevent check-out dates from preceding check-in dates.

For this phase, the widget should create a clearly labelled enquiry intent and direct users to the enquiry flow implemented in a later phase. It must not claim to check live inventory or confirm a reservation.

### C. Accommodation categories

Display cards for:

- Deluxe AC room.
- Standard Non-AC room.
- Dormitory bed.
- Monthly PG stay.

Each card should have a clear description, suitable image or honest placeholder, available confirmed amenities, and a link to its dedicated page.

### D. Trust and convenience

Add reusable sections for:

- Property location and directions.
- Contact and enquiry options.
- Genuine guest feedback, only if real approved review data is available.
- Frequently asked questions based on confirmed business policies.
- Relevant internal links to accommodation pages.

Do not invent review counts, star ratings, guest testimonials, awards, certifications, or guaranteed benefits.

### E. Homepage footer

Use the shared footer from Phase 2 and ensure it links to implemented routes.

## 7. SEO implementation

Use the Next.js Metadata API and the project's existing SEO utilities.

For every implemented route:

- Create a unique, descriptive title.
- Write a relevant meta description.
- Set the canonical URL correctly.
- Configure appropriate Open Graph metadata.
- Use a clear heading hierarchy.
- Add descriptive image alt text based on the actual image.
- Add breadcrumb navigation.
- Link related pages internally.
- Ensure the page is crawlable and renders meaningful HTML without depending on client-side JavaScript for the main content.

Use reusable metadata helpers only if they fit the existing architecture.

Create structured data only when supported by actual content:

- Appropriate hotel/business entity markup on suitable pages.
- BreadcrumbList for breadcrumb navigation.
- FAQPage only for genuine, visible FAQs that meet applicable search-engine guidelines.

Do not fabricate ratings, review data, prices, room inventory, or amenities in JSON-LD.

Ensure existing `sitemap.ts` includes the implemented public routes. Do not list non-existent pages as functioning pages.

## 8. Data architecture

Keep accommodation information in a centralized, typed data module.

Each accommodation entry should support:

- Stable ID and slug.
- Display name.
- Accommodation category.
- Short description.
- Detailed content.
- Price or price status.
- Pricing unit: nightly, per bed, or monthly.
- Amenities.
- Image references.
- SEO title and description.
- Enquiry CTA.
- Publication status.

Use TypeScript types and avoid duplicating room data in multiple components.

Keep unconfirmed fields marked as pending or unavailable. Do not silently treat values from the old documents as verified business facts.

This phase can use typed local data. Do not create a production database schema or booking database in this phase.

## 9. Design and responsive behavior

Follow the approved Phase 2 design system:

- Navy and slate brand colors.
- Amber primary CTAs.
- Outfit headings and Inter body typography.
- Consistent card spacing and border radii.
- Responsive room cards and image layouts.
- Clear booking/enquiry actions.
- Light, dark, and system themes.
- Accessible keyboard focus and visible interactive states.

Check at 320, 375, 640, 768, 1024, 1280, and 1440 pixels.

Prevent horizontal overflow and ensure that mobile sticky actions do not cover forms or important content.

Use `next/image` for suitable local images and configure image handling correctly.

Do not download random hotel images or invent property photography.

## 10. Performance and accessibility

- Keep Server Components as the default.
- Use Client Components only for interactive elements.
- Avoid unnecessary client-side state and large dependencies.
- Avoid layout shifts from images and font loading.
- Provide useful loading and error states for interactive components.
- Use semantic HTML, accessible labels, and meaningful link text.
- Support keyboard navigation and reduced motion.
- Do not claim performance scores without running tests.
