# PHASE 8 — Production Hardening, Security Audit, Performance & Accessibility

## 1. Role and Project Context

Act as a senior software architect, application security engineer, performance engineer, and accessibility specialist.

Continue the existing project:

`hotel-waidhan-singrauli-bnb-nextjs`

Inspect the repository and read the approved strategy plus all available Phase 1–7 implementation reports, architecture documents, security reviews, and test reports.

Preserve all completed features, design decisions, public pages, SEO configuration, database schema, authentication, admin dashboard, booking enquiry workflow, and notification logic.

Do not rebuild the application from scratch. Fix actual issues discovered in the existing implementation.

## 2. Main Objective

Conduct a comprehensive production-readiness audit and improve:

- Application security.
- Authentication and authorization.
- Database access and data protection.
- API reliability.
- Performance and Core Web Vitals.
- Accessibility.
- Mobile responsiveness.
- Technical SEO integrity.
- Error handling and observability.
- Deployment configuration.
- Automated testing and maintainability.

Prioritize real risks and measurable improvements over unnecessary refactoring.

## 3. Security Audit

Inspect the entire application for the following risks:

- Exposed secrets and credentials.
- Incorrect use of public versus server-only environment variables.
- Missing authentication or authorization checks.
- Insecure direct object references.
- SQL injection and unsafe query construction.
- Cross-site scripting (XSS).
- Cross-site request forgery (CSRF), where applicable.
- Open redirects.
- Unvalidated request bodies and query parameters.
- Excessive request payload sizes.
- Public access to private booking enquiries.
- Insecure internal notes or audit-log access.
- Mass assignment of protected database fields.
- Abuse of public booking endpoints.
- Unsafe image URLs or file uploads.
- Sensitive data appearing in logs or error responses.
- Weak cookie and session configuration.
- Insecure dependency versions.
- Overly permissive CORS or Content Security Policy configuration.

Fix confirmed vulnerabilities. Document risks that require external configuration or owner action.

Do not add security controls blindly if they would break legitimate Next.js or Supabase functionality. Verify their compatibility with the current architecture.

## 4. Authentication and Authorization Verification

Test the existing Supabase authentication and role-based permissions.

Verify that:

- Every protected admin page enforces authorization on the server.
- Every mutation checks the current user and their permissions.
- Users cannot elevate their own roles.
- Staff cannot access records beyond their permitted scope.
- Customers cannot read other customers' information.
- Public visitors cannot access audit logs or internal notes.
- Sign-out and session expiration behave correctly.
- Redirects after login do not permit arbitrary external destinations.

Review the implementation of Supabase Row-Level Security and Drizzle access paths. Document any database access paths that bypass user-context RLS and explain the compensating server-side authorization controls.

Do not claim RLS is effective merely because policies exist; test the relevant access paths where credentials and test infrastructure permit.

## 5. API and Database Reliability

Review all existing route handlers, server actions, and database operations.

Implement or improve:

- Consistent input validation using the existing Zod schemas.
- Appropriate HTTP status codes.
- Safe and consistent error responses.
- Pagination limits.
- Database query limits.
- Transaction handling for related changes.
- Safe handling of concurrent booking-status updates.
- Idempotency for relevant retryable operations.
- Rate limiting or a clearly documented integration point.
- Timeouts and bounded retry behavior for external services.
- Appropriate database indexes based on actual query patterns.

Ensure that successful enquiry submission, status changes, and notification processing remain consistent.

Do not lose a persisted enquiry because an email provider is unavailable. Do not report a notification as delivered unless delivery has actually been verified by the provider.

## 6. Security Headers and Browser Protection

Review and configure appropriate security headers, including:

- Content-Security-Policy.
- Strict-Transport-Security for HTTPS production deployments.
- X-Content-Type-Options.
- Referrer-Policy.
- A suitable frame-embedding restriction.
- Permissions-Policy where appropriate.

Requirements:

- Keep the Content Security Policy compatible with actual application assets and integrations.
- Avoid unsafe exceptions where a safer implementation is practical.
- Do not enable HSTS assumptions for an HTTP-only local development environment.
- Restrict third-party scripts and image origins to those genuinely needed.
- Avoid exposing stack traces or internal implementation details in production.

Document any header that requires deployment-platform configuration.

## 7. Performance Optimization

Audit the public website and admin dashboard using actual measurements where available.

Improve:

- Server Component usage and unnecessary client-side JavaScript.
- Route-level code splitting.
- Image sizes, formats, dimensions, and responsive loading.
- Font loading and font-display behavior.
- Layout stability and image aspect ratios.
- Slow database queries and excessive data fetching.
- Duplicate API requests.
- Large client bundles.
- Unnecessary re-renders.
- Excessive third-party scripts.
- Cache behavior for public content versus private data.

Use Next.js Image where appropriate and compatible with the existing image configuration.

Do not cache authenticated customer data, internal notes, or private admin responses in a shared public cache.

Do not introduce Redis or a paid performance service unless necessary and explicitly documented.

### Performance measurements

Where the environment permits, evaluate:

- Largest Contentful Paint (LCP).
- Interaction to Next Paint (INP).
- Cumulative Layout Shift (CLS).
- Lighthouse performance and accessibility scores.
- Bundle size and production build output.

Use these as targets, not fabricated results. Record the device, environment, and testing method when reporting measurements.

## 8. Accessibility Audit

Aim for WCAG 2.2 Level AA for the main user journeys.

Check and fix:

- Semantic page landmarks.
- Heading hierarchy.
- Keyboard navigation.
- Visible focus indicators.
- Color contrast.
- Accessible names for buttons and inputs.
- Form labels and validation errors.
- Screen-reader announcements for submission states.
- Modal focus management and Escape behavior.
- Mobile navigation keyboard behavior.
- Alternative text for meaningful images.
- Decorative images that should be ignored by screen readers.
- Reduced-motion preferences.
- Touch target sizes.
- Tables and status indicators.

Test the important workflows:

1. Browse accommodation categories.
2. Open an accommodation detail page.
3. Submit a booking enquiry.
4. Navigate the contact page.
5. Sign in to the admin dashboard.
6. Update an enquiry status using a keyboard.

Do not rely exclusively on automated accessibility scanners.

## 9. Mobile and Responsive Verification

Test the actual interface at these viewport widths where supported:

- 320 px.
- 375 px.
- 430 px.
- 640 px.
- 768 px.
- 1024 px.
- 1280 px.
- 1440 px.

Verify:

- No unintended horizontal overflow.
- Readable typography.
- Functional navigation.
- Properly sized touch targets.
- Sticky call and WhatsApp actions that do not obscure content.
- Forms that work on mobile keyboards.
- Tables that remain usable on small screens.
- No overlap between banners, headers, dialogs, and floating controls.

Preserve the approved navy, slate, amber, and light-background design system.

## 10. SEO and Public-Page Integrity

Audit all public routes against the approved keyword-to-page mapping and technical SEO checklist.

Verify:

- Unique titles and meta descriptions.
- Canonical URLs.
- Open Graph metadata.
- Correct sitemap entries.
- Correct robots directives.
- Working internal links.
- Breadcrumb consistency.
- Structured data validity.
- Appropriate indexability of utility pages.
- Correct 404 behavior.
- No accidental indexing of admin pages or private enquiry pages.
- No duplicate canonical URLs caused by trailing-slash or host variations.

Only publish structured data supported by actual business information.

Do not invent ratings, review counts, prices, room availability, amenities, or business certifications.

Ensure sitemap entries exclude private admin routes, internal APIs, and non-indexable utility pages.

## 11. Dependency and Supply-Chain Review

Inspect package manifests and lockfiles.

Run available dependency audit tools and identify:

- Known vulnerabilities.
- Outdated critical dependencies.
- Incompatible package versions.
- Unnecessary dependencies.
- Packages with risky installation or runtime behavior.

Upgrade dependencies carefully, keeping Next.js, React, Supabase, Drizzle, and TypeScript compatible.

Do not run blanket major-version upgrades that break the application.

Never suppress an audit finding without documenting the reason and mitigation.

## 12. Error Handling and Monitoring

Create a consistent production error-handling approach.

Implement or improve:

- User-friendly error boundaries.
- Custom not-found handling.
- Safe server-side error logging.
- Correlation or request IDs where useful.
- Monitoring hooks for failed booking submissions.
- Monitoring hooks for failed notification processing.
- Database health diagnostics that do not expose secrets.
- Clear distinction between expected validation errors and unexpected server errors.

If an external monitoring service is not configured, create a clean integration boundary and document setup requirements.

Do not log guest phone numbers, email addresses, credentials, access tokens, internal notes, or full request bodies.

Verify:

- Production build configuration.
- Required environment variables.
- Secure secret handling.
- Database migration procedure.
- Authentication callback and allowed URL configuration.
- Domain and HTTPS assumptions.
- Image host configuration.
- Email provider configuration.
- Cache behavior.
- Health-check strategy.
- Rollback and recovery documentation.

Do not deploy to production, alter DNS, apply destructive migrations, or incur paid service costs without explicit authorization.

Provide a staging deployment checklist if live credentials are unavailable.

## 16. Acceptance Criteria

Phase 8 is complete when:

1. Confirmed critical and high-severity application vulnerabilities have been fixed or explicitly blocked from release.
2. Server-side authorization remains enforced.
3. Private customer data is not publicly exposed or improperly cached.
4. Booking and notification workflows handle failures safely.
5. Public pages and admin workflows remain functional.
6. Major accessibility and mobile usability issues are addressed.
7. Technical SEO remains intact.
8. Performance improvements are supported by measurements where available.
9. Dependency findings and deployment prerequisites are documented.
10. Tests, lint, type-check, build, and available audits have truthful reports.
