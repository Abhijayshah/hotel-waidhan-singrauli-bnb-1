## 4. Drizzle ORM and Database Schema

Create a clean, typed schema organized into logical modules. Include the following entities where appropriate.

### A. User Profiles

Create a profile table associated with the Supabase Auth user ID.

Fields should include:

- ID referencing the authenticated user
- Display name
- Optional phone number
- Role
- Account status
- Created timestamp
- Updated timestamp

Roles should support at least:

- `super_admin`
- `admin`
- `manager`
- `staff`

Use a centralized role and permission definition. New registrations must never be allowed to assign themselves a privileged role.

### B. Accommodation Types

Represent accommodation categories separately from physical room inventory.

Support categories such as:

- Deluxe AC Room
- Standard Room
- Dormitory
- PG Accommodation

These are categories from the website strategy, not confirmation of actual inventory. Do not create fabricated physical room counts, occupancy, amenities, or live availability.

Use a structure that allows the owner to configure accommodation types and descriptions later.

### C. Booking Enquiries

Create a persistent table for customer booking enquiries with fields such as:

- Unique enquiry ID
- Guest name
- Guest contact phone
- Optional email
- Accommodation category or requested accommodation reference
- Check-in date
- Check-out date
- Number of guests
- Optional message
- Enquiry status
- Created timestamp
- Updated timestamp
- Optional staff assignment
- Optional internal notes, accessible only to authorized staff

Use a controlled status set, for example:

- `new`
- `contacted`
- `pending_confirmation`
- `confirmed`
- `cancelled`
- `completed`

A `confirmed` status must only be set by an authorized staff member after the business has actually confirmed the reservation.

Validate that dates are valid, check-out is after check-in, guest counts are within reasonable limits, and all submitted strings have appropriate length limits.

Do not collect payment details or unnecessary sensitive personal information.

### D. Audit Logs

Create an audit log foundation for security-relevant administrative changes, including:

- Actor user ID
- Action
- Resource type
- Resource ID
- Timestamp
- Minimal structured metadata

Never record passwords, access tokens, secrets, or unnecessary guest personal information in audit logs.

Ensure ordinary users cannot create arbitrary audit records to impersonate administrators.

### E. Schema Quality

Use appropriate:

- Primary keys and foreign keys
- Unique constraints
- Check constraints
- Indexes for frequent lookups
- Created and updated timestamps
- Explicit PostgreSQL enums or validated text columns where appropriate

Use safe deletion and retention behavior for records containing customer information.

Do not add fabricated room rates, GST details, inventory counts, or business policies.

## 6. Secure Authentication

Integrate Supabase Auth with the current Next.js App Router architecture.

Implement the appropriate server-side and browser-side Supabase clients. Use the currently recommended SSR cookie-handling pattern rather than deprecated authentication helpers.

Requirements:

- Sign-in and sign-out server actions or route handlers where appropriate.
- Session refresh and cookie handling following current Supabase guidance.
- Server-side retrieval of the authenticated user.
- Protected server-side authorization checks.
- A reusable `requireUser()` helper.
- A reusable `requireRole()` or equivalent permission-checking helper.
- Safe unauthorized and forbidden responses.
- No authorization decisions based solely on client-side state.
- No privileged role assignment from public registration forms.
- No hardcoded test passwords.
- No fake login flow that claims to authenticate users.

If the current website has a login interface, connect it only where appropriate and preserve the existing visual design. Do not build an entire administrative dashboard in this phase.

## 7. Row-Level Security (RLS)

Design and document appropriate PostgreSQL Row-Level Security policies.

Minimum requirements:

- Public visitors cannot read booking enquiries.
- Public visitors cannot read guest contact information.
- Public visitors cannot alter user roles.
- Authenticated customers cannot access other customers' private records.
- Only authorized staff can retrieve or modify administrative enquiry data.
- Audit logs are not publicly readable or writable.
- Accommodation information intended for public display may be readable without authentication, subject to the final schema.

Where public enquiry creation is needed, prefer a controlled server-side API that validates the request and uses narrowly scoped database permissions. Do not solve permission problems by exposing the service-role key.

Explain how the server-side database connection and RLS interact. Do not assume that every Drizzle connection automatically receives the same RLS protections as a Supabase user session.

## 8. Booking Enquiry API

Implement a secure Next.js Route Handler, for example:

`POST /api/booking-enquiries`

The endpoint must:

1. Accept JSON input.
2. Validate the request using a shared Zod schema.
3. Normalize and validate phone numbers without silently changing their meaning.
4. Validate accommodation selection and dates.
5. Reject invalid payloads with clear, safe error messages.
6. Persist valid enquiries to PostgreSQL.
7. Generate the enquiry ID on the server or database.
8. Return a success response with the enquiry reference.
9. Never return internal database errors or stack traces to visitors.
10. Avoid logging guest phone numbers, email addresses, or messages.
11. Include appropriate request-size limits and a practical spam-protection/rate-limiting boundary.
12. Use appropriate HTTP status codes.

Use transaction-safe behavior where necessary.

Do not trust a client-provided price, availability claim, discount, booking status, or staff assignment.

Do not claim that a room is available simply because an enquiry was accepted.

If rate limiting requires an external service that is not configured, document the limitation and provide a clean integration point rather than claiming effective production rate limiting.
