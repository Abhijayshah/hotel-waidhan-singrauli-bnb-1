# PHASE 7 — Booking Workflow, Notifications & Reservation Confirmation

`hotel-waidhan-singrauli-bnb-nextjs`

## 2. Phase Objective

Build a reliable booking-enquiry lifecycle that connects:

- Public website booking forms.
- PostgreSQL persistence through Drizzle ORM.
- The protected staff dashboard.
- Reservation status management.
- Customer acknowledgement notifications.
- Staff notifications.
- Reservation confirmation communication.
- An auditable history of important changes.

The business currently uses an enquiry-first booking model. Customers can submit a request, staff can contact them, and a reservation becomes confirmed only after an authorized person verifies and confirms it.

**A booking enquiry is not a confirmed reservation.** Never claim that a room is available or a reservation is confirmed merely because a form was submitted.

## 3. Define the Booking Lifecycle

Review the Phase 5 database schema and Phase 6 status-handling implementation first.

Create one consistent, documented state-transition model. Adapt the existing statuses rather than introducing duplicate or conflicting status fields.

Recommended lifecycle:

1. `new` — enquiry received.
2. `contacted` — staff contacted the customer.
3. `pending_confirmation` — details are being finalized.
4. `confirmed` — an authorized staff member has confirmed the reservation.
5. `cancelled` — the request or reservation was cancelled.
6. `completed` — the stay has been completed, if the business tracks this.

Define permitted transitions, role permissions, and validation rules centrally.

Requirements:

- Validate every transition on the server.
- Reject invalid or unauthorized transitions.
- Record actor, timestamp, previous state, and new state.
- Prevent public clients from setting `confirmed`, `completed`, or staff-only fields.
- Use database transactions for status changes and associated audit records where appropriate.
- Prevent conflicting concurrent updates using optimistic concurrency or an equivalent safe strategy.
- Do not create a new reservation or duplicate enquiry when staff merely updates an existing record.

Document how cancelled enquiries differ from cancellations of already-confirmed reservations.

## 4. Customer Acknowledgement

After a valid enquiry has been persisted successfully, display a clear acknowledgement to the customer.

Include:

- Enquiry reference number.
- Requested accommodation category.
- Requested dates.
- Number of guests.
- A clear statement that the request has been received but is not yet confirmed.
- Available contact options for following up.

Do not expose internal notes, staff information, private database IDs, or other customers' information.

If an acknowledgement page or confirmation route already exists, reuse it and preserve its SEO configuration. Keep private or utility pages out of search indexing where appropriate.

Do not display a success message if persistence failed.

## 5. Email Notification Architecture

Prepare an email notification layer with a provider abstraction so the application is not tightly coupled to one vendor.

Use a provider such as Resend only if configured and compatible with the existing project.

Support these events where configuration is available:

- New enquiry acknowledgement to the customer.
- New enquiry alert to designated staff.
- Reservation confirmation email after an authorized confirmation.
- Cancellation notification after an authorized cancellation.
- Optional staff notification when an enquiry is assigned.

Create reusable, responsive email templates with:

- Hotel branding.
- Enquiry reference.
- Relevant dates and accommodation information.
- Appropriate contact details from the central site configuration.
- Clear status-specific wording.

Do not invent email addresses or send from an unverified domain.

Requirements:

- Email failures must not silently undo a successfully persisted enquiry.
- Record notification outcomes without logging unnecessary personal information.
- Avoid sending duplicate messages when a request is retried.
- Never send a reservation confirmation email before the reservation has actually been confirmed.
- Do not include internal staff notes in customer emails.
- Do not pretend email delivery is configured if provider credentials are missing.

If the email provider is not configured, implement the provider interface, templates, tests, and setup documentation without claiming that real messages were sent.

## 6. Reliable Notification Processing

Implement a maintainable notification mechanism suitable for a small hotel website.

Prefer a transactional outbox pattern or another reliable design when supported by the current database architecture.

Where appropriate, store:

- Notification event ID.
- Related enquiry ID.
- Event type.
- Recipient category.
- Processing status.
- Attempt count.
- Created and updated timestamps.
- Safe failure details.

Requirements:

- Use idempotency keys or stable event identifiers.
- Prevent duplicate notification processing where practical.
- Retry transient failures with bounded attempts.
- Avoid unbounded retry loops.
- Keep secrets out of logs.
- Do not create a publicly accessible endpoint that can trigger arbitrary emails.
- Restrict retry or administrative operations to trusted server-side processes.

Do not add Redis, a message broker, or a paid queue service unless it is necessary and documented. A simple database-backed implementation is preferred for the initial scale.

If a background worker or scheduler is required, document how it will run in the selected deployment environment. Do not claim a background task is active merely because its code exists.

## 7. Staff Dashboard Integration

Extend the Phase 6 dashboard without replacing it.

Add the operational capabilities required for the workflow:

- Display the current enquiry status.
- Show status-change history.
- Update status through authorized server actions or route handlers.
- Assign enquiries to authorized staff if supported by the schema.
- Show notification state where useful and permitted.
- Clearly distinguish pending enquiries from confirmed reservations.
- Allow staff to retry failed notifications only through a secure, authorized action if retries are supported.

Include pagination, loading states, error states, and empty states.

Use real database records only. Do not populate the production dashboard with fabricated bookings or statistics.

## 8. Concurrency, Duplicate Submissions and Data Integrity

Review the public booking form and API for duplicate requests and race conditions.

Implement suitable protection against accidental duplicate submissions, including:

- Disabling repeat submission while a request is processing.
- Idempotency handling where appropriate.
- Server-side validation.
- Safe database constraints.
- Consistent error handling.

Do not use guest phone numbers alone as unique identifiers. A customer may legitimately submit multiple enquiries.

Do not promise availability based on enquiry records. There is no live inventory allocation in this phase.

## 9. Security and Privacy

Enforce existing Supabase Auth, RBAC, and database access controls.

Requirements:

- Validate all request bodies on the server.
- Verify that only authorized staff can confirm or cancel reservations.
- Prevent mass assignment of protected fields.
- Restrict customer-facing responses to the minimum necessary information.
- Do not expose notification credentials to client code.
- Avoid logging phone numbers, email addresses, internal notes, or complete request payloads.
- Protect staff notification endpoints from unauthorized triggering.
- Apply suitable rate limiting or abuse protection to public submission routes.
- Do not store payment card details or unnecessary sensitive information.

Review retention requirements and document any unresolved data-retention decisions rather than inventing a policy.

## 14. Acceptance Criteria

Phase 7 is complete when:

1. The booking enquiry lifecycle is consistent across the website, API, database, and admin dashboard.
2. Only authorized staff can confirm or cancel reservations.
3. Customers receive an accurate acknowledgement after successful submission.
4. Email notifications are idempotent and safely handled when provider configuration is absent.
5. Notification failures do not incorrectly erase successful enquiries.
6. Status changes are audited.
7. Duplicate submissions and concurrent updates are handled safely.
8. No fake availability, prices, notifications, or confirmations are presented as real.
9. Existing public pages and SEO continue working.
10. Tests, lint, type-check, and build outcomes are documented truthfully.
